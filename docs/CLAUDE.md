Mechanism: `problem_framing` becomes the **mandatory first topic** of the existing refinement interview (not an unbundled pre-DA step — that was superseded), gating "Generate Solutions" until answered; SCQA generation defers until the frame is chosen, then generates against it. Maps each DQ link to fields already present in the SF payload and to existing `src/analysis` instruments; records a **falsifiable prediction before scoring** (links 1 *frame* and 2 *alternatives* fail; 3/5/6 pass; the moderator grades only the links already passing). Chosen over MAP / Vroom-Yetton / KT-DA / AHP for stated reasons: DQ is a *standard*, not a *procedure*, so it grades the artefact without asking a customer to change how they meet |
| `dq_l1_framing_signal_design.md` | **Design note, not built — deliberately not ready to ship.** `score_run()` has no access to the framing gate's persisted decision (`Assumption.framing_choice`) at all; L1 infers "frame examined" purely from vocabulary-scanning SF synthesis text. Found live 2026-08-21: a lens-council run scored 6/6 (first full pass this session), but the naive fix (score L1 off `framing_choice != "confirm_stated"` instead of the vocabulary scan) is a real methodological trap, not a clean win — it conflates "was a different objective chosen" (the framing gate) with "were the solutions structurally widened" (L1's own stated definition), and risks inflating the pass rate as an artifact of the same session's causal-graph work rather than a genuine accuracy fix. Recommends reporting both signals side by side, never collapsed, and running a **held-out validation against the pre-existing 13/33-option corpus this session never touched** before adopting anything — the self-referential risk (validating a scoring change against the one run the same session's fixes just enabled) is named explicitly, not glossed over |
| `kpi_semantic_contract.md` | **Design note, not built.** DGA-governed semantics per KPI — additivity, unit class, sign convention, scope eligibility (§3), plus **sliceability** (§4): which dimensions a KPI must *not* be cut by, as a KPI × dimension deny list derived from `check_slice_validity.py` rather than authored. Turns `groundedness`'s cross-segment-summation *heuristic* into a declared *fact*, and gives the −457% margin-by-customer failure its first check anywhere. No longer parked (Stage H A/B closed); pairs with token substitution |
| `causal_edge_direction_and_magnitude_design.md` | **Direction — built and live (2026-08-20). Magnitude/curve — design note, not built.** Found live 2026-08-20: a Net Revenue framing gate offered "Cost of Goods Sold" as an alternative objective, but COGS has no real relationship to Net Revenue — the only 2-hop path walks the `gross_margin_pct↔cogs` edge *backward* (that edge's own mechanism says COGS causes margin, not the reverse), because `KPIRelationship` has no field encoding which KPI causes which — `kpi_id`/`related_kpi_id` ordering is inconsistent across the existing seed data. Proposes `causal_direction` (filtered at `_build_framing_prompt`, not the shared undirected BFS SA also uses) and `magnitude_category`/`magnitude_coefficient` (mirrors `confidence`'s existing "categorical, not a float" discipline; a real coefficient requires `provenance="va_validated"`, same guardrail pattern as `intervention_tested`) — extends `theory_layer_design.md`'s already-scheduled P1 write-back (verdict + lag) to also cover direction and magnitude, which it doesn't today. An *estimated* (not yet validated) magnitude is still useful — ranking/filtering framing alternatives by strength, and a real data-driven signal for L1 to eventually weigh instead of vocabulary-matching synthesized prose. Curve/non-linear treatment explicitly out of scope — no implementation (VA's or a hypothetical Granger one) would produce it without a materially different method |
| `data_product_time_dimension_planning.md` | **Design note, not built** (interim mitigation shipped). `dp_lubricants_sales` carries three genuinely distinct dates (order/delivery/billing) but `_resolve_time_spec` (`a9_data_product_agent.py:4385`) picks one `primary` time dimension per DATA PRODUCT with no per-KPI override anywhere in the `KPI` model. Proposed general fix (KPI-level `time_dimension_ref` + a `key` slug per time-dimension entry) explicitly deferred as a fast-follow, not pre-demo — narrow and additive, but sits on the core DPA SQL-generation path every workflow depends on |
| `kpi_relationship_basis_design.md` | **Design note, not built.** `KPIRelationship` treats every edge with the same vocabulary (`confidence`/`provenance`/`mechanism`) whether it's a genuinely uncertain causal claim or an accounting identity true by construction — found via the waterfall-chart question on the Framing Evidence Map mockup. Confirmed three misclassified edges in `scripts/clients/lubricants.py`: `net_revenue↔gross_margin_pct` and `gross_margin_pct↔cogs` are pure arithmetic (margin% is calculated from revenue and COGS), and `base_oil_cost→cogs`/`distribution_cost→cogs` are exact `account_category` components of COGS's own `account_type` bucket, confirmed via their own SQL — their mechanism text ("inventory lag," "spot rates") actually describes a different, one-hop-removed external causal claim these edges don't encode. Proposes a `basis: accounting_identity \| causal_estimate` field — determines chart rendering (waterfall vs. causal-graph node) and which edges Phase 17's Core Spine can draw on sooner than that phase's blanket "not built" audit assumed, since FI KPIs' existing `account_type`/`account_category` filters are already an informal, correctly-summing decomposition |
